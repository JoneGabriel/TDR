# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Visão geral

Loja virtual multi-loja (Node.js + Express 5 + MongoDB/Mongoose + Twig) que renderiza vitrines próprias e usa a Shopify como backend de produtos/checkout. Um único servidor atende vários domínios: cada `Domain` aponta para uma `Store`, que guarda configuração visual, idioma, moeda, países e os templates Twig da vitrine. Há também um painel admin em `/admin/*`, protegido por login (JWT em cookie, senha com bcrypt; ver *Autenticação do admin*) e **multiusuário**: cada loja pertence a uma `Account`, usuários têm papel (`superadmin`, `owner`, `staff`) e o cadastro público fica pendente até a aprovação do superadmin (ver *Contas e escopo*).

## Comandos

- `npm install`
- `npm start` — sobe `app.js` com nodemon (recarrega em mudanças `.js` e `.twig`)
- `npm run create-admin -- <usuario> <senha> [superadmin|owner|staff] [idDaConta]` — cria um usuário do painel; sem papel cria um **superadmin** (operador que vê todas as contas) e garante a "Conta principal"
- `npm run migrate-accounts [-- --dry-run]` — migração para multiusuário: cria a Conta principal e liga a ela lojas, lista branca e usuários existentes (idempotente)

Não há build, lint nem testes configurados.

### Variáveis de ambiente (`.env`, não versionado)

`URL_DB` (MongoDB), `PORT`, `HOST`, `ENV` (`DEV` desativa a filtragem de visitantes em `saveSession`), `API_GPT` (OpenAI), `SHOPIFY_API_VERSION` (opcional; padrão em `shopify.client.js`), `JWT_SECRET` (obrigatório para o admin, mínimo 16 caracteres; sem ele o painel fica inacessível), `JWT_EXPIRES` (opcional; padrão `12h`), `ADMIN_HOSTS` (opcional; domínios reservados ao painel separados por vírgula; o host de `HOST` também é reservado), `PUBLIC_IP` (opcional; IP público da VPS para o status de provisionamento dos domínios; sem ele o app consulta `api.ipify.org`), `TRUST_PROXY` (opcional; proxies confiáveis na frente do app para o `X-Forwarded-For`: padrão `1` = só o nginx do compose, `2` com Cloudflare na frente, `false` sem proxy; nunca `true`, que deixa o visitante forjar o próprio IP), `IPWHOIS_KEY` (chave do ipwhois.pro usada pelo filtro de visitantes; sem ela o app usa a chave antiga que ficou no código e avisa no log: troque a chave no ipwhois e configure), `BODY_LIMIT` (opcional; corpo JSON das rotas públicas, padrão `1mb`), `BODY_LIMIT_ADMIN` (opcional; corpo das rotas de escrita do painel com imagens em base64, padrão `200mb`), `PRICES_REFRESH_HOURS` (opcional; intervalo do job de preços por país, padrão `24`, `0` desliga), `API_KEY_17TRACK` (opcional; chave do 17TRACK para o rastreio ao vivo na página do pedido; vazio desliga), `TRACKING_TTL_MINUTES` (opcional; padrão `30`).

## Deploy na VPS (Docker)

Tudo em `docker-compose.yml` é para produção na VPS, não para desenvolvimento local (guia passo a passo em `DEPLOY.md`). A VPS guarda só a pasta de deploy (`Dockerfile`, `docker-compose.yml`, `nginx/`, `scripts/`, `.env`): o `Dockerfile` **clona o código do GitHub dentro do build** (estágio `source`: args `GIT_REPO`, `GIT_BRANCH`, `CACHEBUST`; token via secret de build `git_token`, que o compose lê de `GIT_TOKEN` no `.env` e entrega só em `/run/secrets` durante o `git clone`, sem virar camada da imagem; `.git` é removido e o hash fica em `.build-commit`), depois `npm ci --omit=dev` (estágio `deps`) e a imagem final Node 22 slim com usuário `node`, `node app.js` e healthcheck em `GET /health` (rota em `app.js` que não toca no banco). `.dockerignore` é `*` porque nada da pasta local entra na imagem. Serviços: `app`, `mongo` (mongo:7 com autenticação `MONGO_USER`/`MONGO_PASSWORD`, sem porta publicada; o compose define `MONGO_HOST=mongo`, `MONGO_DB=TDR` e repassa `MONGO_USER`/`MONGO_PASSWORD` do `.env` ao app, e `dbUrl()` em `src/query.js` monta a URL com `encodeURIComponent` no usuário e na senha, ignorando `URL_DB`; sem `MONGO_HOST`, vale `URL_DB`), `nginx` (1.27-alpine, portas 80/443) e `certs-init` (certificado autoassinado para o HTTPS subir antes do certbot). `certbot` só roda com `--profile certs`.

Nginx (`nginx/`): `nginx.conf` (gzip, `client_max_body_size 200m`, `resolver 127.0.0.11` para re-resolver o IP do container `app` a cada 10s, parâmetros TLS no `http{}`, inclui `conf.d/*.conf` e `sites/*.conf`); `templates/default.conf.template` é o catch-all `server_name _` renderizado por envsubst com `TDR_SSL_CERT`, `TDR_SSL_KEY` e `TDR_HTTP_MODE` (`app` inclui `snippets/http-app.conf`, `redirect` inclui `snippets/http-redirect.conf`, cujo `return 301` fica dentro de `location /` para não engolir o desafio ACME); `site.conf.template` e `site-redirect.conf.template` geram um arquivo por domínio em `nginx/sites/` (ignorado pelo git); snippets: `proxy.conf` (X-Forwarded-*, timeouts de 300s para refresh de preços, IA e chat), `app.conf` (`set $tdr_app http://app:3000` + `proxy_pass $tdr_app`), `static.conf` (estáticos repassados ao app com `Cache-Control` definido pelo nginx: vendor/img/video 7 dias, scripts/styles 10 min; o nginx não lê `public/` do disco porque o código só existe na imagem) e `ssl.conf` (cabeçalhos de segurança). O app resolve a loja pelo `Host` exato (`getConfigStore(req.get('host'),'domain')`), então `loja.com` e `www.loja.com` são domínios distintos em `/admin/domain`.

**Status de provisionamento no painel** (`/admin/domain`): o app não provisiona nada (isso é o `sync`), só observa. `checkDomain(host, active)` em `src/domain/domain.service.js` resolve o A do domínio (`dns.resolve4`), compara com o IP público da VPS (`serverIp()`: `PUBLIC_IP` ou `api.ipify.org`, cache de 1 h) e faz `GET https://<ip>/health` com SNI do domínio e `rejectUnauthorized:false` para ler o certificado e avaliar à mão (`socket.authorized`, `tls.checkServerIdentity`, validade), produzindo `state`: `dns_pending` (não resolve), `dns_other` (A em outro IP), `ssl_pending` (DNS ok, nginx ainda serve o autoassinado do `certs-init`), `ssl_error`, `unreachable` (443 não responde), `other_app` (SSL válido mas a resposta não é o `/health` do TDR), `ready`, `inactive`, `local`, com `label` e `message` em pt-BR (prazos: propagação de minutos a 48 h, SSL em até `SYNC_MINUTES` = 10 min, o intervalo do cron). `GET /domain/:id/check` roda a verificação e grava em `Domain.check`; `GET /domain/server-ip` devolve o IP para o registro A; `POST /domain` responde `{_id, domain, server_ip, sync_minutes}`. `domain-admin.js` relista com o último `check`, reverifica em segundo plano (3 por vez: pendentes sempre, "pronto" só se tiver mais de 30 min) e repete a cada minuto com a aba visível; após cadastrar mostra o painel `[c-id=dns-help]` (registro A + IP com botão copiar + prazos) e começa a acompanhar a linha; cada linha tem o botão `[c-id=btn-check]`.

Scripts de operação (bash, rodam na pasta de deploy da VPS): `scripts/domain.sh sync` é o caminho normal (cron a cada 10 min): lê os hosts ativos da coleção `domains` via `docker compose exec app node -e` (mongoose, vale para Mongo local ou Atlas), agrupa por domínio raiz (`www.` removido), só emite quando o DNS de todos os hosts cadastrados resolve para o IP público da VPS, inclui a contraparte apex/www no certificado com redirect para o host cadastrado quando o DNS dela também aponta para cá, grava `nginx/sites/<apex>.conf` com a primeira linha `# tdr-sync names=... app=... redirects=...` (assinatura para detectar mudanças), remove blocos `tdr-sync` cujo domínio saiu do painel, não toca em blocos criados por `add`, guarda falhas do certbot em `nginx/sites/.sync-state/<apex>.failed` com backoff de 1h, usa `flock` para não rodar em paralelo e faz um único `nginx -t` + reload no fim; flags `--dry-run`, `--no-dns-check`, `--staging`, `--delete-cert`. Comandos manuais: `add|remove|list|renew|render <dominio> [--to-www|--no-www|--staging|--email]` (e-mail em `CERTBOT_EMAIL` no `.env`), `scripts/deploy.sh [--restart]` (rebuild com `CACHEBUST=$(date +%s)` para forçar um clone novo, up, espera healthcheck, reload do nginx), `scripts/backup-mongo.sh` (mongodump gzip em `backups/`, mantém 14). `.env.docker.example` é o modelo do `.env` (formato `KEY=valor`). A pasta de deploy inteira (`Dockerfile`, `docker-compose.yml`, `.dockerignore`, `nginx/`, `scripts/*.sh`, `.env.docker.example`) fica **fora do git** por decisão do projeto (`.gitignore`): ela existe na máquina de desenvolvimento e na VPS (`/opt/tdr`), e é copiada por `scp`. Só `scripts/create-admin.js`, `DEPLOY.md` e este arquivo são versionados.

## Arquitetura

### Carregamento automático de rotas
[src/controller.js](src/controller.js) percorre cada pasta de `src/` e monta `src/<dir>/<dir>.controller.js` se existir. Um novo módulo só precisa seguir essa convenção de nome e exportar um `Router`; não é preciso registrá-lo em `app.js`. Rota não encontrada: sob `/admin` (ou em host reservado do painel) redireciona para `/admin/home`; na vitrine, para `/`.

### Padrão de módulo
Cada domínio em `src/<nome>/` tem `*.controller.js` (rotas JSON), `*.service.js` (regras) e `*.schema.js` (models Mongoose).

- Services retornam `statusHandler.newResponse(status, content)` e, em erro, fazem `throw(statusHandler.serviceError(error))`; controllers respondem `res.status(response.status).send(response)` e usam `statusHandler.responseError(error, res)` no `catch` ([src/helpers/helpers.statusHandler.js](src/helpers/helpers.statusHandler.js)). Para erros de negócio: `throw(statusHandler.newResponse(400, 'mensagem'))`. `serviceError`/`responseError` passam o erro por `fromMongoose`: `ValidationError` e `CastError` do Mongoose viram **400** com o campo traduzido (`FIELD_LABELS`: "Preço: obrigatório", "Idioma: valor não permitido (ZZ)"), em vez do 500 "Internal Error" de antes; o restante continua 500. As guardas de escopo (`account.service.js`, `byId`) tratam id malformado como inexistente (404). **Produto**: `normalizeProductInput(product, creating)` em `product.service.js` roda no início de `createProduct`/`changeProduct`: título e preço obrigatórios, números aceitam vírgula decimal ("19,90"), comparação de preços vazia vira igual ao preço (sem desconto), versão second com número vazio é descartada, bundle totalmente vazio é ignorado e bundle preenchido exige título, preço e quantidade inteira (mensagens "Bundle \"Kit\": ..."); falha na Shopify ao buscar variantes responde com a URL da loja e o motivo (`Shopify x.myshopify.com: Not Found (loja inexistente ou token sem acesso)`). No admin, `saveProduct` lança `Error` com a mensagem do servidor e o botão salvar mostra o toast uma vez, com o modal aberto.
- Acesso ao banco passa por [src/query.js](src/query.js) (`findAll`, `findById`, `save`, `updateById`, `populate`, `aggregate`...), que chama `mongoose.connect(dbUrl())` a cada operação; `dbUrl()` usa `URL_DB` ou, quando `MONGO_HOST` está definido (Docker), monta a URL a partir de `MONGO_USER`/`MONGO_PASSWORD`/`MONGO_DB` com escape. Use esses helpers em vez de chamar o model diretamente.
- Chamadas HTTP externas usam `request(method, url, data, headers)` de [src/helpers/helpers.global.js](src/helpers/helpers.global.js), que **não lança exceção**: devolve o corpo de erro ou `{status:500, ...}`.
- Datas salvas são deslocadas manualmente para UTC-3 (horário de Brasília) antes de gravar.

### Renderização (vitrine e admin)
Todas as páginas HTML ficam em [src/render/render.controller.js](src/render/render.controller.js) e renderizam o layout único [src/template/index.twig](src/template/index.twig), passando:
- `template`: a string do conteúdo da página;
- `script`: o arquivo de `public/scripts/` carregado na página;
- `admin: true` ou `store: true` para escolher o layout.

**Admin**: `template` é um `{% include %}` de `src/components/admin/*.twig`, e o JS da tela está em `public/scripts/*-admin.js`, que chama as rotas JSON. Os modais seguem um padrão: cabeçalho com título (`<b c-id="name-...">` + `.modal-title-fallback`), corpo em `section.modal-section` (título `.modal-section-title`, dica `.modal-section-hint`) e rodapé fixo com o botão salvar e o spinner `loading-btn`. **Salvar não fecha o modal**: a lista atrás é atualizada e o formulário continua aberto; um registro novo passa a ser editado no ato (os creates de loja, produto, coleção, Shopify, domínio e lista branca devolvem `{_id, ...}` e o script grava o `_id` no botão salvar, que é de onde os submodais da loja leem o id). Produto, coleção, Shopify e domínio recarregam o formulário do servidor após salvar (`getXById`), o produto para pegar os ids novos de bundles e variantes; a loja só troca o id, o título e revela os botões de template/políticas (assim o layout em edição não muda). O modal de IP da lista branca é só de inclusão: fica aberto e limpo para o próximo. Os botões "Adicionar" limpam o formulário antes de abrir e "Fechar" limpa ao fechar. Imagens passam por `public/scripts/admin-media.js` (`AdminMedia`): compressão no navegador (até 1600px, WEBP), área `.dropzone` com arrastar e soltar, grade `.media-grid` com reordenação por arraste (a primeira é a capa, `set-cover` move para o início), `.image-picker` para imagem única (logo, banners: card que é a zona de soltar quando vazio e vira a própria imagem quando preenchido, com `[c-id=view-img]`, `[c-id=replace-img]` e `[c-id=remove-img]` em `.media-actions`; `store-admin.js` liga o `bindDropzone` ao card inteiro e `showImage` marca o card com `has-image`, fallback para navegadores sem `:has()`) e contador por `MutationObserver`. Visualização: `AdminMedia.openLightbox(items, index)` cria um lightbox (`.media-lightbox`, navegação por setas/Esc) aberto pelo botão `[c-id=view-img]` ou por duplo clique na miniatura; na grade navega entre as fotos irmãs. Metadados (`.media-meta`: dimensões e tamanho) são preenchidos por um listener de `load` em captura, e as miniaturas são numeradas por contador CSS. A integração de geração de imagens por IA (Higgsfield/MCP) foi removida: não há mais rotas `/ai/*`, página Integrações nem barras "Gerar com IA". O JS continua se apoiando nos mesmos `c-id` (`model-img`, `image-list`, `remove-img`, `img-logo`, `banner-N`...).

**Vitrine**: cada loja tem **dois layouts**, `first` e `second`, cada um com o conjunto completo de templates (`header_template`, `menu_store`, `cart_template`, `footer_template`, `home_template`, `collection_template`, `product_template`, `order_template`). Eles **ficam no documento `Store` do MongoDB**, em `layouts.first.*` e `layouts.second.*`, não em arquivos. Quem escolhe o layout é o filtro de visitantes: `saveSession(req, res, config)` (`trail.service.js`) devolve `true` para visitante liberado, que vê `first`, e `false` para visitante filtrado (país fora de `Store.country`, dispositivo fora de `Store.devices`, proxy/VPN/hosting, org Google), que vê `second`. **Dispositivos atendidos** são configuráveis por loja como os países: `Store.devices` (`mobile`, `tablet`, `desktop`; catálogo, `deviceOf(req.useragent)` e `allowedDevices` em [src/helpers/helpers.devices.js](src/helpers/helpers.devices.js)); lista vazia ou loja antiga sem o campo usa o padrão `mobile`+`tablet` (o comportamento original: desktop filtrado; no express-useragent tablet também é `isMobile`), `normalizeDevices` em `store.service.js` recusa salvar sem nenhum dispositivo, o modal da loja tem a seção "Dispositivos atendidos" (`[c-id=devices]`, `options_devices`) e a sessão grava `device`; não há redirect para `https://www.<host>`. `?layout=first|second` na URL pré-visualiza um layout, mas só para visitante liberado (com `ENV=DEV` todos são). Os padrões estão em `defaultLayout` ([src/store/store.schema.js](src/store/store.schema.js)) e são materializados nos dois layouts em `createStore`; o admin edita via `GET/PUT /store-config/:idStore/:idFile?layout=first|second` (lista em `files` de `store.service.js`; sem `layout` assume `first`). `getConfigStore(id, type)` devolve `config` com `config.layouts.{first,second}` já resolvidos (fallback: `layouts.<nome>.<campo>` → campo legado na raiz do documento, só para `first` → padrão) e com `first` aplicado na raiz; `useLayout(config, nome)` troca o layout copiando os templates para a raiz, por isso as rotas de `render.controller.js` continuam lendo `config.header_template` etc. Cada rota compila essas strings com `Twig.twig({data}).render(...)` antes de injetá-las em `index.twig`. No `catch`, as rotas da vitrine respondem com `src/components/store/error.twig` (página standalone, sem depender de `config`) via `renderError`: `getConfigStore` lança `newResponse(404, ...)` para id inválido, produto/coleção/domínio inexistente, sem loja vinculada ou loja apagada, e a página sai com esse status e texto "Page not found" sem stack no log; qualquer outro erro é 500 com o erro completo no log. Alterar o default no schema não afeta lojas já criadas. **Produtos por layout**: a raiz do documento `Product` é a versão `first`; `layouts.second` guarda a versão `second` (`name`, `last_price`, `price`, `images`, `description`). `applyProductLayout(product, layout)` em [src/product/product.service.js](src/product/product.service.js) devolve o produto na versão do layout em uso (campo vazio em `second` cai na `first`) e é aplicado em `getFirtsCollection`, `getInfoCollection`, `getProductById` (vitrine), `getProductsRamdon` e `getProductByIdForCart`; **na loja second só aparecem produtos com versão second cadastrada** (ao menos um campo de `layouts.second` preenchido): `SECOND_VERSION_FILTER`/`layoutFilter(layout)` entra nas consultas das listas e `assertVisibleInLayout(id, layout)` responde 404 na página do produto e no carrinho (`/product/cart/:id`); as rotas de `render.controller.js` passam `config.layout`, **exceto `/order/:id`**, que fica fora dessa regra. O carrinho (`cart.js`) envia `layout` lido de `<body data-layout>` (definido em `index.twig`). O admin edita as duas versões no mesmo formulário (`products.twig`, seção "Versão second"); `normalizeProductLayouts` descarta campos vazios de `layouts.second` ao salvar, e `GET /product/:id` (admin) devolve o documento inteiro, com `layouts`. Bundles, variantes Shopify, coleção e loja são compartilhados entre as versões. **Visual por layout**: `title` (título do navegador), `logo`, `position_logo`, `banner_1..3`, `css`, `message_top` e todas as cores (`color_*`/`bk_*`, `color_icons`, `color_n_items_cart`) variam por layout (lista em `visualFields()` de `store.schema.js`). A raiz do documento `Store` guarda os valores do `first` (seletor "Layout: First | Second" no topo do modal da loja; as seções por layout levam o selo `layout-tag`) e `layouts.second.*` guarda só o que o `second` sobrescreve (vazio herda do first: o admin mostra imagem herdada esmaecida com o selo "herdado do first", cor herdada esmaecida com borda tracejada e classe `is-inherited`, e texto herdado como placeholder; o botão "Herdar mensagem e cores do first" limpa as cores do second). `resolveLayout` resolve esses campos com `own[key] || doc[key]`, e o título com `own.title || doc.title || doc.name` (não existe mais `config.title = name` em `getConfigStore`); `useLayout` copia tudo para a raiz de `config`, então `{{title}}`, `{{logo}}`, `{{banner_1}}`, `{{color_btn_product}}` e o `{{css}}` de `head.twig` já saem no layout em uso. No `PUT /store-config/:id`, `changeStore` passa o corpo por `layoutsToUpdate`: `layouts` aninhado vira caminhos pontuados (`$set` para valor preenchido, `$unset` para vazio), para nunca substituir o subdocumento inteiro e apagar os templates. Produtos: `ensureProductStore` em `product.service.js` herda a loja da coleção quando o body não traz `store` e recusa com 400 se não houver loja. **Moeda base no formulário de produto**: `getAllStores` (`GET /store-config`) devolve cada loja com `currency` (ISO, via `baseCurrencyOf(moeda)`: `legacyMoeda` ou EUR, a mesma regra da vitrine) e `currency_symbol`; `products-admin.js` guarda `storesById`/`collectionsById` e `applyCurrencySymbol()` escreve o símbolo nos prefixos `[c-id=currency-symbol]` (`.currency-group`) dos preços first, second e dos bundles, seguindo a loja escolhida ou a loja da coleção (`¤` com `is-unknown` enquanto não há loja).

As páginas de políticas (`/privacy-policy`, `/shipping-policy`, `/return-refund`, `/terms-of-service`) usam `src/components/store/policies.twig` com `config.policies.<chave>` (`title_policy`, `text_policy`), resolvido por `resolvePolicies` em `store.service.js`: texto gravado em `Store.policies.<chave>` ou, se vazio, o padrão de `policies[país]` (país da loja; sem texto para o país usa o do idioma: FR→FR, ES→ES, demais→GB). O admin edita cada política no modal "Políticas" da loja via `GET/PUT /store-config/:idStore/policy/:chave` (chaves `privacy`, `shipping`, `return`, `terms`); salvar com título e texto vazios remove a personalização e volta ao padrão. Diferente dos templates, as políticas não são materializadas na criação da loja: seguem o padrão do país até serem editadas.

`getConfigStore(id, type)` resolve a loja a partir do host (`'domain'`), de um produto (`'product'`) ou de uma coleção (`'collection'`) e converte `idioma`/`moeda` em seus dicionários de tradução/símbolo. Em erro, as rotas da vitrine respondem com a página `error.twig` via `renderError` (não há mais redirect para `https://www.<host>`).

### Preços por país (moedas)
- Catálogo de países, moedas, fusos IANA e localidades de data em [src/helpers/helpers.countries.js](src/helpers/helpers.countries.js) (41 países; `timeZoneOf(code)`/`localeOf(code)` com padrão Paris/en-GB). Datas da página do pedido, do rastreio e do chat usam o país do endereço de entrega do pedido (`pickDateCountry` em `order.service.js`, `order.date_country`/`order.time_zone`) e, se ele não estiver no catálogo, o primeiro país da loja; `fmtDate(value, country, withTime)` formata nesse fuso/localidade, e `now` do template do pedido segue o mesmo fuso; `Store.country` aceita qualquer um deles e o admin lista todos. O primeiro país da loja é o padrão de moeda e checkout.
- O TDR **nunca converte moeda**: [src/pricing/pricing.service.js](src/pricing/pricing.service.js) consulta a Storefront API com `@inContext(country)` e guarda o que a Shopify devolveu (preço já com câmbio/arredondamento/preço fixo do mercado) em `OtherVariants.variants.variant_values[].prices[país]`, o menor preço do produto em `Product.prices[país]` (cards) e a moeda real por país em `Store.market_currencies`. O refresh roda ao criar/editar produto (`createProduct`/`changeProduct`), no job diário (`startPricesRefreshJob` em `app.js`, fora de `DEV` também 2 min após subir) e pelo botão "Atualizar preços" do admin (`POST /pricing/refresh`, `POST /pricing/refresh/:productId`).
- Na visita, `saveSession` expõe `req.visitorCountry` (ipwhois/geoip-lite) e `useCountry(config, país)` em `store.service.js` define `config.buyer_country`, `config.currency` e o símbolo em `config.moeda` (regra: moeda de `market_currencies[país]`; sem refresh para o país, a moeda base da loja, para símbolo e preço nunca divergirem). `?country=XX` pré-visualiza outro país atendido. `applyProductLayout(product, layout, país)` aplica `prices[país]` só no layout `first`; `localizeVariants` faz o mesmo nas variantes para `/product/variant/:id?country=`, `/product/cart/:id` (`body.country`) e o checkout (`POST /checkout?country=`), que cria o carrinho com `buyerIdentity.countryCode` desse país, garantindo a mesma moeda no checkout. Bundles têm preço manual na moeda base e são convertidos pela razão preço local/preço base da variante (`countryRatio`); use cupons percentuais para o checkout bater.
- Página e cliente: `<body data-country data-currency>` em `index.twig`; `product.js` e `cart.js` enviam o país nas chamadas JSON.

### Página do pedido e chat de suporte
`GET /order/:id?urlStore=<sub>` renderiza `order_template` com o pedido da Admin API (`getOrderShopify` em [src/order/order.service.js](src/order/order.service.js)): valores, endereço, rastreio, eventos da transportadora e previsão; A data do pedido exibida (`order.createdAt` formatado, `order.createdAtISO`) vem de `processedAt`, o mesmo campo que o painel da Shopify mostra como data do pedido (momento do pagamento); `createdAt` da Shopify fica em `order.createdRecordISO` e pode ser posterior. `enrichOrder` calcula `order.stage` (processing → shipped → in_transit → delivered, ou cancelled), `order.timeline`, `order.tracking`, `order.last_event`, `order.labels` (idioma da loja). O chat (`public/scripts/order.js`) é injetado no modal "Problemas com meu pedido" (`[c-id=chat-root]` no template novo; antes do formulário nos antigos) e recebe o contexto por `window.TDR_ORDER` (`getChatContext`, impresso em `index.twig`). API pública: `GET /order/chat/:id` (histórico ou saudação determinística `buildGreeting`, sem IA) e `POST /order/chat/:id` {urlStore, message}: `sendChat` monta o prompt com os fatos reais do pedido e trechos das políticas (`buildSystemPrompt`), chama a OpenAI (`API_GPT`, `GPT_MODEL` padrão `gpt-5`, resposta JSON `{reply, suggestions, action}`) e guarda a conversa em `OrderChat` (limite de 40 mensagens). Regras do prompt: nunca inventar eventos, locais ou rastreio; devolução/defeito/reembolso → `action: open_form`; `show_tracking` rola até o rastreio. Por loja, `Store.support` (nome da assistente, cupom de fidelidade, instruções) é editado na seção "Atendimento" do modal da loja. `/order/support/:id` (legado) devolve só a saudação. **Rastreio ao vivo (17TRACK)**: módulo [src/tracking/](src/tracking/). `getTrackings(order.tracking, {force, order})` em `tracking.service.js` registra cada código uma vez no 17TRACK (`POST /register`, API v2.4, header `17token`; "já registrado" conta como sucesso), lê `gettrackinfo`, normaliza (`status`, `latest_event`, `events` do mais novo ao mais antigo, `estimated_from/to`, `days_in_transit`, transportador) e guarda em `Tracking` (um documento por código); só consulta de novo após `TRACKING_TTL_MINUTES` ou com `force` (mínimo 2 min), nunca para status `Delivered`, e em erro mantém o cache e registra `error`. `getOrderShopify` chama `attachLiveTracking`, que aplica o cache ao pedido (`applyLiveTracking`): `order.live_tracking` (textos de `t.track`, datas no país), estágio da linha do tempo refinado (Delivered → delivered, em trânsito/incidente → in_transit, InfoReceived → shipped), `last_event`/`estimated_delivery_fmt`/`delivered_at_fmt` como fallback quando a Shopify não tem, `tracking_problem`. O prompt do chat recebe os fatos do transportador. Página: `getChatContext` injeta `tracking:{items, labels}` em `window.TDR_ORDER`; `order.js` renderiza o painel em `[c-id=tracking-root]` (âncora no template padrão) ou no fim de `.order-tracking` nos templates antigos, com status, previsão, histórico (4 eventos, "ver todos"), link para a transportadora ou 17TRACK e botão "Atualizar" → `GET /order/tracking/:idOrder?urlStore=&refresh=1` (pública; só rastreia os códigos do próprio pedido). **Modo dropshipping (global, não configurável)**: a API do 17TRACK não tem o "Hide all China info" do app da Shopify, então o filtro é nosso, em `tracking.service.js` (`ORIGIN_COUNTRIES` CN/HK/MO, `ORIGIN_PLACE`, `ORIGIN_EVENT`, `ORIGIN_CARRIER`, `ORIGIN_URL`; helpers `isOriginCountry/isOriginCarrier/isOriginUrl/isOriginPlace`): `normalize` marca cada evento com `origin:true` quando o provedor é chinês ou o evento tem país/cidade/descrição de origem, guarda só a transportadora de última milha (`misc_info.local_provider` ou o primeiro provedor fora da origem) e `hidden_events`; `present` entrega só eventos visíveis, esconde `company`/`url` da Shopify quando são de origem, nunca gera link para o 17TRACK e marca `international:true` quando só há eventos ocultos e o pacote ainda não chegou ao destino (texto `t.track.international`). `enrichOrder` aplica o mesmo filtro aos `trackingInfo` e aos eventos sincronizados pela Shopify (estágio continua calculado com todos os eventos). O prompt do chat proíbe citar origem, cidades chinesas, alfândega de exportação e transportadoras de primeiro trecho. Textos do chat por idioma em `chatI18n` (FR, EN, DE, NL, ES), incluindo o bloco `track` do rastreio. Idiomas da loja (`Store.idioma`, enum em `store.schema.js`): FR, EN, DE, NL, ES; para adicionar um idioma: enum, bloco em `idioma` e `options_idioma` de `store.service.js`, bloco em `chatI18n`, locais de data em `order.service.js` e, se houver país próprio, políticas em `policies` + `byIdioma` de `defaultPoliciesFor`.

### Métricas e sessões
- **Sessão** = documento `Trail` ([src/trail/trail.service.js](src/trail/trail.service.js)). O visitante é identificado pelo cookie first-party `tdr_vid` (HttpOnly, 1 ano), criado em `saveSession(req, res, config)` nas rotas da vitrine (o config da loja traz `country`, `devices` e `account`; as formas antigas `saveSession(req, res, country, account)` e `saveSession(req, country)` continuam aceitas). Uma sessão dura enquanto houver atividade com intervalo menor que 30 min (`SESSION_WINDOW_MS`); cada página soma `pageviews` e entra em `pages`/`last_path`; a decisão do cloaker (`page` white/black, `layout`) é tomada uma vez por sessão e reaproveitada. Bots (`isbot`) são gravados com `is_bot:true` e ignorados em todas as contagens. IPs da white list não geram sessão. Em `ENV=DEV` a sessão é gravada e todo visitante é liberado (sem consulta de IP). Se o ipwhois falhar, `geoip-lite` preenche país/cidade (`geo_source`) só para as métricas: a decisão do cloaker continua dependendo do ipwhois.
- **Eventos**: a vitrine envia `POST /add-cart` e `POST /init-checkout` (`cart.js`, sempre, com `keepalive`) e `POST /heartbeat` a cada 30s com a aba visível (`public/scripts/session.js`). `createNewEvent` marca `added_cart`/`init_checkout` na sessão ativa (uma vez por sessão) e grava um `Event` ligado a ela (`session`, `visitor`, `product`, `path`); `pingSession` só renova `lastSeenAt`.
- **Painel** (`/admin/home`, `home-admin.js`): `GET /metrics/summary?start=YYYY-MM-DD&end=YYYY-MM-DD&domain=` devolve totais, funil (sessões únicas), taxas, série por hora (um dia) ou por dia (intervalo), páginas, países e dispositivos; `GET /metrics/realtime?domain=` devolve as sessões com atividade nos últimos 5 min. Datas: o banco guarda horário de Brasília deslocado (UTC-3), então um dia local é `00:00Z–23:59:59Z` do mesmo valor. As rotas antigas `/session`, `/session/interval` e `/metrics` continuam existindo, mas o painel não as usa mais. Cores das séries do gráfico validadas para o fundo escuro: `#13a7bc`, `#b8309a`, `#c2860c`.

### Exclusão definitiva no admin
Cada listagem tem uma lixeira (`c-id="btn-delete"`) que abre o modal de confirmação de `src/template/confirm-admin.twig` via `confirmAction()` (`public/scripts/helpers.js`) e chama a rota `DELETE`: `/store-config/:id`, `/product/:id`, `/collection/:id`, `/domain/:id`, `/store/:id` (Shopify) e `/cloacker/white-list/:id`. É remoção real, não desativação. Regras nos services: produto apaga em cascata suas `OtherVariants` e `Bundle`; loja, coleção e Shopify respondem 400 enquanto houver itens vinculados (loja: domínios/produtos/coleções/Shopifys; coleção: produtos; Shopify: `OtherVariants`), para não deixar órfãos. `removeMany(schema, query)` em `src/query.js` faz o `deleteMany`. Dentro dos modais (bundle e Shopify do produto) continua o `confirm()` nativo, para não empilhar modais do Bootstrap.

### Contas e escopo (multiusuário)
Módulo [src/account/](src/account/). `Account` (`account.schema.js`): nome, e-mail, `status` (`pending` no cadastro público, `active` após aprovação, `blocked`), datas de aprovação. `Admin` ganhou `account` e `role` (`superadmin` sem conta vê tudo; `owner` é o dono; `staff` é usuário comum e não cria usuários). `Store.account` é o dono da loja; domínios, coleções, produtos, bundles, variantes e Shopifys pertencem à conta **pela loja** (`store`), e `white_list`, `White_Page` e `Setting` têm `account` próprio. Migração: `scripts/migrate-accounts.js` cria a "Conta principal" e liga a ela tudo o que não tem dono (usuários existentes viram superadmin; remove o índice único antigo de `settings.key`).

**Sessão**: o JWT leva `role` e `account`; tokens antigos sem `role` são tratados como ausentes (novo login). `loadContext` em `auth.service.js` monta `req.admin`, `req.scope` e `res.locals.admin_user` (menu) e consulta o status da conta com cache de 30 s (`accountInfo`/`forgetAccount`): conta pendente ou bloqueada vai para `/admin/pending` nas páginas e recebe 403 nas APIs; conta bloqueada nem faz login. `req.scope` é a conta em uso: a do usuário, ou, para o superadmin, a conta em que ele "entrou" (cookie `admin_as`, rotas `POST /accounts/:id/impersonate`, `POST /accounts/leave`, página `/admin/leave-account`) ou `null` = todas. Middlewares: `requireAdminPage`, `requireAdminApi`, `requireScope` (ações que exigem uma conta: criar loja, IP da lista branca), `requireSuperadmin`/`requireSuperadminPage`.

**Cadastro e aprovação**: `GET/POST /admin/register` (`register.twig`) cria a conta pendente e o usuário dono, já logado, e manda para `/admin/pending` (`pending.twig`). Superadmin aprova, bloqueia ou reativa em `/admin/accounts` (`accounts.twig`, `accounts-admin.js`; API `GET /accounts`, `PUT /accounts/:id/status`), com contagens de lojas, domínios, produtos e usuários por conta. `POST /admin/users`: dono cria `staff` da própria conta; superadmin cria em qualquer conta (ou outro superadmin).

**Escopo nos dados** (`account.service.js`): `storeIdsOf(scope)`/`storeFilter(scope)` para listas (`getAllStores`, `getAllDomains`, `getAllShopify`, `getAllProducts`, `getAllCollections`, `getAllIps`, `refreshAllPrices`) e guardas por id usadas nos controllers antes de qualquer leitura, edição ou exclusão (`assertStore`, `assertDomain`, `assertCollection`, `assertProduct`, `assertShopify`, `assertBundle`, `assertOtherVariant`, `assertIp`; corpo de produto passa por `assertProductBody`): fora do escopo respondem 404 sem revelar que o registro existe. Métricas: `domainNamesOf(scope)` limita `getSummary`/`getRealtime`/rotas antigas aos domínios da conta (domínio pedido fora dela é 404). Cloaker: a lista branca libera só nas lojas da própria conta (`config.account` em `saveSession(req, res, config)`). Vitrine, checkout, pedido, chat e rastreio continuam públicos e resolvem a loja pelo domínio. O superadmin fora de uma conta vê e edita tudo, mas para criar loja ou IP precisa "entrar" numa conta. Teste de referência: um script que cria duas contas e tenta cada rota do painel com os ids da outra (todas devem dar 404).

### Autenticação do admin
Módulo [src/auth/](src/auth/). Usuários ficam na coleção `Admin` (`auth.schema.js`) com `password` em hash bcrypt (custo 10); o primeiro é criado com `npm run create-admin`, os demais via `POST /admin/users` (autenticado). `POST /admin/login` valida com `bcrypt.compare`, assina um JWT com `role` e `account` (`jsonwebtoken`, `JWT_SECRET`, validade `JWT_EXPIRES`) e grava no cookie `admin_token` (`HttpOnly`, `SameSite=Lax`, `Secure` quando a requisição é HTTPS); `GET /admin/logout` limpa o cookie. Dois middlewares em `auth.service.js`: `requireAdminPage` (páginas `/admin/*` em `render.controller.js`; sem sessão redireciona para `/admin/login`) e `requireAdminApi` (rotas JSON do painel; sem sessão responde 401). A proteção das rotas JSON é declarada no topo de cada controller com `router.use(prefixo, requireAdminApi)`, exceto em `product.controller.js`, onde é por rota porque `POST /product/cart/:id` e `POST /product/variant/:id` são usados pela vitrine. Continuam públicos: toda a vitrine, `/checkout*`, `/order/support/:id`, `/order/charge`, `/add-cart` e `/init-checkout`. `public/scripts/helpers.js` redireciona para o login quando uma chamada do admin recebe 401. **Área do usuário** (`/admin/profile`, `profile.twig`, `profile-admin.js`; o link é o nome do usuário no menu): mostra usuário, papel, conta e datas, edita o e-mail e troca a senha. API em `auth.controller.js`: `GET /admin/me`, `PUT /admin/me` {email} e `PUT /admin/me/password` {current_password, password, password_confirm} (`getProfile`/`updateProfile`/`changePassword` em `auth.service.js`, pelo `sub` do JWT; exige a senha atual, mínimo 8, confirmação igual e diferente da atual; grava `Admin.password_changed_at`). Usuário e papel não mudam por aí, e a troca de senha não invalida as sessões abertas (o JWT não depende da senha). **Domínios reservados ao sistema**: `reservedHosts()` em `auth.service.js` = `ADMIN_HOSTS` + host de `HOST` (localhost e IPs ficam de fora); `isReservedHost(host)` compara também a variante `www.`. Nesses hosts as rotas de vitrine de `render.controller.js` levam o middleware `notOnAdminHost` e redirecionam para `/admin/home` (que leva ao login sem sessão). Fallback de rota inexistente em `app.js`: caminho sob `/admin` ou host reservado → `/admin/home`; demais → `/`; `createDomain`/`changeDomain` (`checkDomainName` em `domain.service.js`) recusam com 400 cadastrar um host reservado como domínio de loja. As rotas JSON não são afetadas.

### Segurança (sistema multi-inquilino)
- **Templates dos inquilinos são código executado no servidor**: [src/helpers/helpers.twig-sandbox.js](src/helpers/helpers.twig-sandbox.js), carregado em `app.js`, usa `Twig.extend` para desativar `source()` (lia qualquer arquivo, inclusive o `.env`) e `template_from_string()`, trocar `attribute()` por uma versão que só devolve propriedades próprias (nunca `constructor`/`__proto__` nem funções), nunca executar valores-função alcançados por chave (`x.constructor`, `doc.deleteOne()`, macros viram vazio) e recusar `nome()` quando `nome` é uma função do contexto. Vale para toda renderização (vitrine e painel). Qualquer novo `Twig.twig(...)` já nasce protegido; não reative essas funções.
- **Escape no painel**: o renderer do Express roda com `autoescape:true`, então tudo o que os `.twig` do admin imprimem sai escapado (nomes de loja/produto/coleção/domínio de um inquilino aparecem como texto para o superadmin). O HTML já renderizado da vitrine e o CSS passam por `|raw` em `index.twig`, `head.twig`, `footer.twig` e `policies.twig`; as páginas do painel e de políticas são incluídas por `{% include view %}` com caminho relativo a `src/template` (`view:'../components/...'` no controller). Não existe mais `template_from_string(template)` no layout.
- **Corpo das requisições** (`app.js`): 1 MB nas rotas públicas, 15 MB no formulário de problema do pedido (`/order/charge`, que só aceita `idOrder`, `email`, `justification` e até 5 imagens `data:image/*` de 2 MB) e `BODY_LIMIT_ADMIN` só em `POST/PUT` de `/product`, `/product/:id`, `/store-config*` e `/collection*`, e só depois de `requireAdminApi` confirmar a sessão (sem login o corpo grande nem é lido).
- **Limites de taxa** em memória por IP ([src/helpers/helpers.ratelimit.js](src/helpers/helpers.ratelimit.js), `rateLimit({name, windowMs, max, methods, onLimit})`): login 20/15 min e cadastro 5/h (formulário recebe a própria página com a mensagem, JSON recebe 429), chat do pedido 30/5 min, rastreio 20/min, formulário de problema 10/10 min, checkout 30/min, eventos da vitrine 120/min. Dependem de `req.ip`, logo de `TRUST_PROXY`.
- **Sessão**: JWT só HS256 (`algorithms:["HS256"]`), com `tv` = `Admin.token_version`; `loadContext` consulta `adminInfo` (cache de 30 s) e derruba a sessão de usuário desativado ou com `tv` antigo. Trocar a senha incrementa `token_version`, limpa o cache e reemite o cookie da sessão atual (as outras caem).
- **Domínios**: `checkDomainName` aceita só hostname RFC 1123 (o nome vai para o Host, para o nginx e para o certbot via `domain.sh`, que também valida com `norm_host`); a verificação de provisionamento não sonda IPs privados/reservados (`isPrivateIp`, estado `dns_other`).
- **Mass assignment**: `changeStore` descarta `account` e `_id` do corpo; produtos/coleções/domínios/Shopifys passam pelas guardas de escopo (`assert*`).
- **Pendências conhecidas** (não corrigidas): a página pública `/order/:id?urlStore=` identifica o pedido só pelo id numérico da Shopify (quem adivinhar um id vê endereço e e-mail do cliente; o ideal é um token assinado no link do e-mail); `Trail.cookies` guarda o cabeçalho Cookie dos visitantes; `GET /admin/logout` e `GET /admin/leave-account` mudam estado por GET; `npm audit` ainda aponta `twig` 1.x (via `locutus`/`minimatch`, partes não usadas pelo app; a correção é o `twig` 3, que precisa de teste), `geoip-lite` (via `ip-address`) e `nodemon` (dev).

### Integração com Shopify
- Toda chamada à Shopify passa por `shopifyGraphql(shopify, "admin" | "storefront", query, variables)` em [src/shopify/shopify.client.js](src/shopify/shopify.client.js), que define a versão da API (`SHOPIFY_API_VERSION`, trimestral) e resolve os tokens. Use variáveis GraphQL, nunca interpolação de strings.
- `Shopify` (schema) representa uma loja Shopify. Apps do Dev Dashboard usam `client_id`/`client_secret` (client credentials grant, token Admin de 24h em cache na memória); apps legados criados no admin usam `token_admin` fixo. Se `token_storefront` estiver vazio, ele é criado via `storefrontAccessTokenCreate` e salvo.
- Variantes: Storefront API em `product.service.js` (`getVariants`). Checkout: `POST /checkout` → `cartCreate` + `cartDiscountCodesUpdate` em `cart.service.js` (cupom inválido volta com `applicable: false`, não em `userErrors`); `/checkout/pagou` é um fluxo alternativo (Pagou.ai). Pedidos: Admin API em `order.service.js`, que remapeia a resposta para o formato antigo usado pelos templates (`customer.email`, `variant.image`).
