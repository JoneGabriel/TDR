# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Visão geral

Loja virtual multi-loja (Node.js + Express 5 + MongoDB/Mongoose + Twig) que renderiza vitrines próprias e usa a Shopify como backend de produtos/checkout. Um único servidor atende vários domínios: cada `Domain` aponta para uma `Store`, que guarda configuração visual, idioma, moeda, países e os templates Twig da vitrine. Há também um painel admin em `/admin/*`, protegido por login (JWT em cookie, senha com bcrypt; ver *Autenticação do admin*).

## Comandos

- `npm install`
- `npm start` — sobe `app.js` com nodemon (recarrega em mudanças `.js` e `.twig`)
- `npm run create-admin -- <usuario> <senha>` — cria um usuário do painel admin (necessário antes do primeiro login)

Não há build, lint nem testes configurados.

### Variáveis de ambiente (`.env`, não versionado)

`URL_DB` (MongoDB), `PORT`, `HOST`, `ENV` (`DEV` desativa a filtragem de visitantes em `saveSession`), `API_GPT` (OpenAI), `SHOPIFY_API_VERSION` (opcional; padrão em `shopify.client.js`), `JWT_SECRET` (obrigatório para o admin, mínimo 16 caracteres; sem ele o painel fica inacessível), `JWT_EXPIRES` (opcional; padrão `12h`), `ADMIN_HOSTS` (opcional; domínios exclusivos do painel separados por vírgula; vazio desliga o recurso), `PRICES_REFRESH_HOURS` (opcional; intervalo do job de preços por país, padrão `24`, `0` desliga), `HIGGSFIELD_MCP_URL` (opcional; padrão `https://mcp.higgsfield.ai/mcp`).

## Deploy na VPS (Docker)

Tudo em `docker-compose.yml` é para produção na VPS, não para desenvolvimento local (guia passo a passo em `DEPLOY.md`). A VPS guarda só a pasta de deploy (`Dockerfile`, `docker-compose.yml`, `nginx/`, `scripts/`, `.env`): o `Dockerfile` **clona o código do GitHub dentro do build** (estágio `source`: args `GIT_REPO`, `GIT_BRANCH`, `CACHEBUST`; token via secret de build `git_token`, que o compose lê de `GIT_TOKEN` no `.env` e entrega só em `/run/secrets` durante o `git clone`, sem virar camada da imagem; `.git` é removido e o hash fica em `.build-commit`), depois `npm ci --omit=dev` (estágio `deps`) e a imagem final Node 22 slim com usuário `node`, `node app.js` e healthcheck em `GET /health` (rota em `app.js` que não toca no banco). `.dockerignore` é `*` porque nada da pasta local entra na imagem. Serviços: `app`, `mongo` (mongo:7 com autenticação `MONGO_USER`/`MONGO_PASSWORD`, sem porta publicada; o compose define `MONGO_HOST=mongo`, `MONGO_DB=TDR` e repassa `MONGO_USER`/`MONGO_PASSWORD` do `.env` ao app, e `dbUrl()` em `src/query.js` monta a URL com `encodeURIComponent` no usuário e na senha, ignorando `URL_DB`; sem `MONGO_HOST`, vale `URL_DB`), `nginx` (1.27-alpine, portas 80/443) e `certs-init` (certificado autoassinado para o HTTPS subir antes do certbot). `certbot` só roda com `--profile certs`.

Nginx (`nginx/`): `nginx.conf` (gzip, `client_max_body_size 200m`, `resolver 127.0.0.11` para re-resolver o IP do container `app` a cada 10s, parâmetros TLS no `http{}`, inclui `conf.d/*.conf` e `sites/*.conf`); `templates/default.conf.template` é o catch-all `server_name _` renderizado por envsubst com `TDR_SSL_CERT`, `TDR_SSL_KEY` e `TDR_HTTP_MODE` (`app` inclui `snippets/http-app.conf`, `redirect` inclui `snippets/http-redirect.conf`, cujo `return 301` fica dentro de `location /` para não engolir o desafio ACME); `site.conf.template` e `site-redirect.conf.template` geram um arquivo por domínio em `nginx/sites/` (ignorado pelo git); snippets: `proxy.conf` (X-Forwarded-*, timeouts de 300s para refresh de preços, IA e chat), `app.conf` (`set $tdr_app http://app:3000` + `proxy_pass $tdr_app`), `static.conf` (estáticos repassados ao app com `Cache-Control` definido pelo nginx: vendor/img/video 7 dias, scripts/styles 10 min; o nginx não lê `public/` do disco porque o código só existe na imagem) e `ssl.conf` (cabeçalhos de segurança). O app resolve a loja pelo `Host` exato (`getConfigStore(req.get('host'),'domain')`), então `loja.com` e `www.loja.com` são domínios distintos em `/admin/domain`.

Scripts de operação (bash, rodam na pasta de deploy da VPS): `scripts/domain.sh sync` é o caminho normal (cron a cada 10 min): lê os hosts ativos da coleção `domains` via `docker compose exec app node -e` (mongoose, vale para Mongo local ou Atlas), agrupa por domínio raiz (`www.` removido), só emite quando o DNS de todos os hosts cadastrados resolve para o IP público da VPS, inclui a contraparte apex/www no certificado com redirect para o host cadastrado quando o DNS dela também aponta para cá, grava `nginx/sites/<apex>.conf` com a primeira linha `# tdr-sync names=... app=... redirects=...` (assinatura para detectar mudanças), remove blocos `tdr-sync` cujo domínio saiu do painel, não toca em blocos criados por `add`, guarda falhas do certbot em `nginx/sites/.sync-state/<apex>.failed` com backoff de 1h, usa `flock` para não rodar em paralelo e faz um único `nginx -t` + reload no fim; flags `--dry-run`, `--no-dns-check`, `--staging`, `--delete-cert`. Comandos manuais: `add|remove|list|renew|render <dominio> [--to-www|--no-www|--staging|--email]` (e-mail em `CERTBOT_EMAIL` no `.env`), `scripts/deploy.sh [--restart]` (rebuild com `CACHEBUST=$(date +%s)` para forçar um clone novo, up, espera healthcheck, reload do nginx), `scripts/backup-mongo.sh` (mongodump gzip em `backups/`, mantém 14). `.env.docker.example` é o modelo do `.env` (formato `KEY=valor`). A pasta de deploy inteira (`Dockerfile`, `docker-compose.yml`, `.dockerignore`, `nginx/`, `scripts/*.sh`, `.env.docker.example`) fica **fora do git** por decisão do projeto (`.gitignore`): ela existe na máquina de desenvolvimento e na VPS (`/opt/tdr`), e é copiada por `scp`. Só `scripts/create-admin.js`, `DEPLOY.md` e este arquivo são versionados.

## Arquitetura

### Carregamento automático de rotas
[src/controller.js](src/controller.js) percorre cada pasta de `src/` e monta `src/<dir>/<dir>.controller.js` se existir. Um novo módulo só precisa seguir essa convenção de nome e exportar um `Router`; não é preciso registrá-lo em `app.js`. Qualquer rota não encontrada redireciona para `/`.

### Padrão de módulo
Cada domínio em `src/<nome>/` tem `*.controller.js` (rotas JSON), `*.service.js` (regras) e `*.schema.js` (models Mongoose).

- Services retornam `statusHandler.newResponse(status, content)` e, em erro, fazem `throw(statusHandler.serviceError(error))`; controllers respondem `res.status(response.status).send(response)` e usam `statusHandler.responseError(error, res)` no `catch` ([src/helpers/helpers.statusHandler.js](src/helpers/helpers.statusHandler.js)). Para erros de negócio: `throw(statusHandler.newResponse(400, 'mensagem'))`.
- Acesso ao banco passa por [src/query.js](src/query.js) (`findAll`, `findById`, `save`, `updateById`, `populate`, `aggregate`...), que chama `mongoose.connect(dbUrl())` a cada operação; `dbUrl()` usa `URL_DB` ou, quando `MONGO_HOST` está definido (Docker), monta a URL a partir de `MONGO_USER`/`MONGO_PASSWORD`/`MONGO_DB` com escape. Use esses helpers em vez de chamar o model diretamente.
- Chamadas HTTP externas usam `request(method, url, data, headers)` de [src/helpers/helpers.global.js](src/helpers/helpers.global.js), que **não lança exceção**: devolve o corpo de erro ou `{status:500, ...}`.
- Datas salvas são deslocadas manualmente para UTC-3 (horário de Brasília) antes de gravar.

### Renderização (vitrine e admin)
Todas as páginas HTML ficam em [src/render/render.controller.js](src/render/render.controller.js) e renderizam o layout único [src/template/index.twig](src/template/index.twig), passando:
- `template`: a string do conteúdo da página;
- `script`: o arquivo de `public/scripts/` carregado na página;
- `admin: true` ou `store: true` para escolher o layout.

**Admin**: `template` é um `{% include %}` de `src/components/admin/*.twig`, e o JS da tela está em `public/scripts/*-admin.js`, que chama as rotas JSON. Os modais seguem um padrão: cabeçalho com título (`<b c-id="name-...">` + `.modal-title-fallback`), corpo em `section.modal-section` (título `.modal-section-title`, dica `.modal-section-hint`) e rodapé fixo com o botão salvar e o spinner `loading-btn`. Imagens passam por `public/scripts/admin-media.js` (`AdminMedia`): compressão no navegador (até 1600px, WEBP), área `.dropzone` com arrastar e soltar, grade `.media-grid` com reordenação por arraste (a primeira é a capa, `set-cover` move para o início), `.image-picker` para imagem única (logo, banners) e contador por `MutationObserver`. O JS continua se apoiando nos mesmos `c-id` (`model-img`, `image-list`, `remove-img`, `img-logo`, `banner-N`...).

**Vitrine**: cada loja tem **dois layouts**, `first` e `second`, cada um com o conjunto completo de templates (`header_template`, `menu_store`, `cart_template`, `footer_template`, `home_template`, `collection_template`, `product_template`, `order_template`). Eles **ficam no documento `Store` do MongoDB**, em `layouts.first.*` e `layouts.second.*`, não em arquivos. Quem escolhe o layout é o filtro de visitantes: `saveSession` (`trail.service.js`) devolve `true` para visitante liberado, que vê `first`, e `false` para visitante filtrado (país fora da lista da loja, proxy/VPN/hosting, desktop, org Google), que vê `second`; não há redirect para `https://www.<host>`. `?layout=first|second` na URL pré-visualiza um layout, mas só para visitante liberado (com `ENV=DEV` todos são). Os padrões estão em `defaultLayout` ([src/store/store.schema.js](src/store/store.schema.js)) e são materializados nos dois layouts em `createStore`; o admin edita via `GET/PUT /store-config/:idStore/:idFile?layout=first|second` (lista em `files` de `store.service.js`; sem `layout` assume `first`). `getConfigStore(id, type)` devolve `config` com `config.layouts.{first,second}` já resolvidos (fallback: `layouts.<nome>.<campo>` → campo legado na raiz do documento, só para `first` → padrão) e com `first` aplicado na raiz; `useLayout(config, nome)` troca o layout copiando os templates para a raiz, por isso as rotas de `render.controller.js` continuam lendo `config.header_template` etc. Cada rota compila essas strings com `Twig.twig({data}).render(...)` antes de injetá-las em `index.twig`. No `catch`, as rotas da vitrine respondem com `src/components/store/error.twig` (página standalone, sem depender de `config`) via `renderError`: `getConfigStore` lança `newResponse(404, ...)` para id inválido, produto/coleção/domínio inexistente, sem loja vinculada ou loja apagada, e a página sai com esse status e texto "Page not found" sem stack no log; qualquer outro erro é 500 com o erro completo no log. Alterar o default no schema não afeta lojas já criadas. **Produtos por layout**: a raiz do documento `Product` é a versão `first`; `layouts.second` guarda a versão `second` (`name`, `last_price`, `price`, `images`, `description`). `applyProductLayout(product, layout)` em [src/product/product.service.js](src/product/product.service.js) devolve o produto na versão do layout em uso (campo vazio em `second` cai na `first`) e é aplicado em `getFirtsCollection`, `getInfoCollection`, `getProductById` (vitrine), `getProductsRamdon` e `getProductByIdForCart`; as rotas de `render.controller.js` passam `config.layout`, **exceto `/order/:id`**, que fica fora dessa regra. O carrinho (`cart.js`) envia `layout` lido de `<body data-layout>` (definido em `index.twig`). O admin edita as duas versões no mesmo formulário (`products.twig`, seção "Versão second"); `normalizeProductLayouts` descarta campos vazios de `layouts.second` ao salvar, e `GET /product/:id` (admin) devolve o documento inteiro, com `layouts`. Bundles, variantes Shopify, coleção e loja são compartilhados entre as versões. **Visual por layout**: `logo`, `position_logo`, `banner_1..3` e `css` também variam por layout. A raiz do documento `Store` guarda os valores do `first` (aba "First" do modal da loja) e `layouts.second.*` guarda só o que o `second` sobrescreve (aba "Second"; vazio herda do first, e o admin mostra a imagem herdada esmaecida com o selo "herdado do first"). `resolveLayout` resolve esses campos com `own[key] || doc[key]` e `useLayout` os copia para a raiz de `config`, então `{{logo}}`, `{{banner_1}}` e o `{{css}}` de `head.twig` já saem no layout em uso. No `PUT /store-config/:id`, `changeStore` passa o corpo por `layoutsToUpdate`: `layouts` aninhado vira caminhos pontuados (`$set` para valor preenchido, `$unset` para vazio), para nunca substituir o subdocumento inteiro e apagar os templates. Produtos: `ensureProductStore` em `product.service.js` herda a loja da coleção quando o body não traz `store` e recusa com 400 se não houver loja.

As páginas de políticas (`/privacy-policy`, `/shipping-policy`, `/return-refund`, `/terms-of-service`) usam `src/components/store/policies.twig` com `config.policies.<chave>` (`title_policy`, `text_policy`), resolvido por `resolvePolicies` em `store.service.js`: texto gravado em `Store.policies.<chave>` ou, se vazio, o padrão de `policies[país]` (país da loja; sem texto para o país usa o do idioma: FR→FR, ES→ES, demais→GB). O admin edita cada política no modal "Políticas" da loja via `GET/PUT /store-config/:idStore/policy/:chave` (chaves `privacy`, `shipping`, `return`, `terms`); salvar com título e texto vazios remove a personalização e volta ao padrão. Diferente dos templates, as políticas não são materializadas na criação da loja: seguem o padrão do país até serem editadas.

`getConfigStore(id, type)` resolve a loja a partir do host (`'domain'`), de um produto (`'product'`) ou de uma coleção (`'collection'`) e converte `idioma`/`moeda` em seus dicionários de tradução/símbolo. Em erro, as rotas da vitrine respondem com a página `error.twig` via `renderError` (não há mais redirect para `https://www.<host>`).

### Preços por país (moedas)
- Catálogo de países e moedas em [src/helpers/helpers.countries.js](src/helpers/helpers.countries.js) (41 países); `Store.country` aceita qualquer um deles e o admin lista todos. O primeiro país da loja é o padrão de moeda e checkout.
- O TDR **nunca converte moeda**: [src/pricing/pricing.service.js](src/pricing/pricing.service.js) consulta a Storefront API com `@inContext(country)` e guarda o que a Shopify devolveu (preço já com câmbio/arredondamento/preço fixo do mercado) em `OtherVariants.variants.variant_values[].prices[país]`, o menor preço do produto em `Product.prices[país]` (cards) e a moeda real por país em `Store.market_currencies`. O refresh roda ao criar/editar produto (`createProduct`/`changeProduct`), no job diário (`startPricesRefreshJob` em `app.js`, fora de `DEV` também 2 min após subir) e pelo botão "Atualizar preços" do admin (`POST /pricing/refresh`, `POST /pricing/refresh/:productId`).
- Na visita, `saveSession` expõe `req.visitorCountry` (ipwhois/geoip-lite) e `useCountry(config, país)` em `store.service.js` define `config.buyer_country`, `config.currency` e o símbolo em `config.moeda` (regra: moeda de `market_currencies[país]`; sem refresh para o país, a moeda base da loja, para símbolo e preço nunca divergirem). `?country=XX` pré-visualiza outro país atendido. `applyProductLayout(product, layout, país)` aplica `prices[país]` só no layout `first`; `localizeVariants` faz o mesmo nas variantes para `/product/variant/:id?country=`, `/product/cart/:id` (`body.country`) e o checkout (`POST /checkout?country=`), que cria o carrinho com `buyerIdentity.countryCode` desse país, garantindo a mesma moeda no checkout. Bundles têm preço manual na moeda base e são convertidos pela razão preço local/preço base da variante (`countryRatio`); use cupons percentuais para o checkout bater.
- Página e cliente: `<body data-country data-currency>` em `index.twig`; `product.js` e `cart.js` enviam o país nas chamadas JSON.

### Integração Higgsfield (imagens por IA)
Módulo [src/ai/](src/ai/). O MCP da Higgsfield (`https://mcp.higgsfield.ai/mcp`, Streamable HTTP) exige OAuth 2.1: `ai.service.js` implementa o `OAuthClientProvider` do SDK `@modelcontextprotocol/sdk` (registro dinâmico do cliente, PKCE, refresh token) guardando cliente, tokens, `state`/`code_verifier` e conta em `Setting` (chave `higgsfield`, `ai.schema.js`). Fluxo: `POST /ai/connect` registra o cliente com `redirect_uri = <origem do admin>/ai/oauth/callback` e devolve a URL de autorização; o admin autoriza no navegador; `GET /ai/oauth/callback` troca o code pelos tokens. Tela `/admin/integrations` (`integrations.twig`, `integrations-admin.js`): conectar/testar/desconectar e padrões (modelo, proporção, qualidade, `use_unlim`). Geração: `POST /ai/image` {prompt, aspect_ratio?} inicia um job em memória que chama `generate_image_batch`, faz polling com `jobs_wait` (até 180s), baixa o `result_url` e guarda como data URL; `GET /ai/image/:id` dá o status e `GET /ai/image/:id/file` a imagem. No admin, `AdminMedia.bindAiBar` (`admin-media.js`) liga a barra `.ai-bar` (`c-id="ai-bar-*"`, `data-aspect`) de cada área de imagem: fotos do produto e da versão second, imagem da coleção, logo e banners da loja; a imagem gerada passa pela mesma compressão de um upload e entra pelo mesmo caminho (`listImg`, `listLogo`, `listBanner`). Erros de "não conectada" respondem 409 (401 derrubaria a sessão do painel no `helpers.js`). Rotas `/ai/*` exigem admin; o callback usa `requireAdminPage`.

### Página do pedido e chat de suporte
`GET /order/:id?urlStore=<sub>` renderiza `order_template` com o pedido da Admin API (`getOrderShopify` em [src/order/order.service.js](src/order/order.service.js)): valores, endereço, rastreio, eventos da transportadora e previsão; `enrichOrder` calcula `order.stage` (processing → shipped → in_transit → delivered, ou cancelled), `order.timeline`, `order.tracking`, `order.last_event`, `order.labels` (idioma da loja). O chat (`public/scripts/order.js`) é injetado no modal "Problemas com meu pedido" (`[c-id=chat-root]` no template novo; antes do formulário nos antigos) e recebe o contexto por `window.TDR_ORDER` (`getChatContext`, impresso em `index.twig`). API pública: `GET /order/chat/:id` (histórico ou saudação determinística `buildGreeting`, sem IA) e `POST /order/chat/:id` {urlStore, message}: `sendChat` monta o prompt com os fatos reais do pedido e trechos das políticas (`buildSystemPrompt`), chama a OpenAI (`API_GPT`, `GPT_MODEL` padrão `gpt-5`, resposta JSON `{reply, suggestions, action}`) e guarda a conversa em `OrderChat` (limite de 40 mensagens). Regras do prompt: nunca inventar eventos, locais ou rastreio; devolução/defeito/reembolso → `action: open_form`; `show_tracking` rola até o rastreio. Por loja, `Store.support` (nome da assistente, cupom de fidelidade, instruções) é editado na seção "Atendimento" do modal da loja. `/order/support/:id` (legado) devolve só a saudação. Textos do chat por idioma em `chatI18n` (FR, EN, DE, NL, ES). Idiomas da loja (`Store.idioma`, enum em `store.schema.js`): FR, EN, DE, NL, ES; para adicionar um idioma: enum, bloco em `idioma` e `options_idioma` de `store.service.js`, bloco em `chatI18n`, locais de data em `order.service.js` e, se houver país próprio, políticas em `policies` + `byIdioma` de `defaultPoliciesFor`.

### Métricas e sessões
- **Sessão** = documento `Trail` ([src/trail/trail.service.js](src/trail/trail.service.js)). O visitante é identificado pelo cookie first-party `tdr_vid` (HttpOnly, 1 ano), criado em `saveSession(req, res, config.country)` nas rotas da vitrine. Uma sessão dura enquanto houver atividade com intervalo menor que 30 min (`SESSION_WINDOW_MS`); cada página soma `pageviews` e entra em `pages`/`last_path`; a decisão do cloaker (`page` white/black, `layout`) é tomada uma vez por sessão e reaproveitada. Bots (`isbot`) são gravados com `is_bot:true` e ignorados em todas as contagens. IPs da white list não geram sessão. Em `ENV=DEV` a sessão é gravada e todo visitante é liberado (sem consulta de IP). Se o ipwhois falhar, `geoip-lite` preenche país/cidade (`geo_source`) só para as métricas: a decisão do cloaker continua dependendo do ipwhois.
- **Eventos**: a vitrine envia `POST /add-cart` e `POST /init-checkout` (`cart.js`, sempre, com `keepalive`) e `POST /heartbeat` a cada 30s com a aba visível (`public/scripts/session.js`). `createNewEvent` marca `added_cart`/`init_checkout` na sessão ativa (uma vez por sessão) e grava um `Event` ligado a ela (`session`, `visitor`, `product`, `path`); `pingSession` só renova `lastSeenAt`.
- **Painel** (`/admin/home`, `home-admin.js`): `GET /metrics/summary?start=YYYY-MM-DD&end=YYYY-MM-DD&domain=` devolve totais, funil (sessões únicas), taxas, série por hora (um dia) ou por dia (intervalo), páginas, países e dispositivos; `GET /metrics/realtime?domain=` devolve as sessões com atividade nos últimos 5 min. Datas: o banco guarda horário de Brasília deslocado (UTC-3), então um dia local é `00:00Z–23:59:59Z` do mesmo valor. As rotas antigas `/session`, `/session/interval` e `/metrics` continuam existindo, mas o painel não as usa mais. Cores das séries do gráfico validadas para o fundo escuro: `#13a7bc`, `#b8309a`, `#c2860c`.

### Exclusão definitiva no admin
Cada listagem tem uma lixeira (`c-id="btn-delete"`) que abre o modal de confirmação de `src/template/confirm-admin.twig` via `confirmAction()` (`public/scripts/helpers.js`) e chama a rota `DELETE`: `/store-config/:id`, `/product/:id`, `/collection/:id`, `/domain/:id`, `/store/:id` (Shopify) e `/cloacker/white-list/:id`. É remoção real, não desativação. Regras nos services: produto apaga em cascata suas `OtherVariants` e `Bundle`; loja, coleção e Shopify respondem 400 enquanto houver itens vinculados (loja: domínios/produtos/coleções/Shopifys; coleção: produtos; Shopify: `OtherVariants`), para não deixar órfãos. `removeMany(schema, query)` em `src/query.js` faz o `deleteMany`. Dentro dos modais (bundle e Shopify do produto) continua o `confirm()` nativo, para não empilhar modais do Bootstrap.

### Autenticação do admin
Módulo [src/auth/](src/auth/). Usuários ficam na coleção `Admin` (`auth.schema.js`) com `password` em hash bcrypt (custo 10); o primeiro é criado com `npm run create-admin`, os demais via `POST /admin/users` (autenticado). `POST /admin/login` valida com `bcrypt.compare`, assina um JWT (`jsonwebtoken`, `JWT_SECRET`, validade `JWT_EXPIRES`) e grava no cookie `admin_token` (`HttpOnly`, `SameSite=Lax`, `Secure` quando a requisição é HTTPS); `GET /admin/logout` limpa o cookie. Dois middlewares em `auth.service.js`: `requireAdminPage` (páginas `/admin/*` em `render.controller.js`; sem sessão redireciona para `/admin/login`) e `requireAdminApi` (rotas JSON do painel; sem sessão responde 401). A proteção das rotas JSON é declarada no topo de cada controller com `router.use(prefixo, requireAdminApi)`, exceto em `product.controller.js`, onde é por rota porque `POST /product/cart/:id` e `POST /product/variant/:id` são usados pela vitrine. Continuam públicos: toda a vitrine, `/checkout*`, `/order/support/:id`, `/order/charge`, `/add-cart` e `/init-checkout`. `public/scripts/helpers.js` redireciona para o login quando uma chamada do admin recebe 401. **Domínios do painel**: `adminHosts()`/`isAdminHost(req)` em `auth.service.js` leem `ADMIN_HOSTS` (sem fallback: vazio desliga); um host listado não pode ser domínio de loja; nesses hosts as rotas de vitrine de `render.controller.js` levam o middleware `notOnAdminHost` e redirecionam para `/admin/login`, e o fallback de rota inexistente em `app.js` também (nos demais hosts continua indo para `/`). As rotas JSON não são afetadas.

### Integração com Shopify
- Toda chamada à Shopify passa por `shopifyGraphql(shopify, "admin" | "storefront", query, variables)` em [src/shopify/shopify.client.js](src/shopify/shopify.client.js), que define a versão da API (`SHOPIFY_API_VERSION`, trimestral) e resolve os tokens. Use variáveis GraphQL, nunca interpolação de strings.
- `Shopify` (schema) representa uma loja Shopify. Apps do Dev Dashboard usam `client_id`/`client_secret` (client credentials grant, token Admin de 24h em cache na memória); apps legados criados no admin usam `token_admin` fixo. Se `token_storefront` estiver vazio, ele é criado via `storefrontAccessTokenCreate` e salvo.
- Variantes: Storefront API em `product.service.js` (`getVariants`). Checkout: `POST /checkout` → `cartCreate` + `cartDiscountCodesUpdate` em `cart.service.js` (cupom inválido volta com `applicable: false`, não em `userErrors`); `/checkout/pagou` é um fluxo alternativo (Pagou.ai). Pedidos: Admin API em `order.service.js`, que remapeia a resposta para o formato antigo usado pelos templates (`customer.email`, `variant.image`).

### Frontend
jQuery + Bootstrap 5 servidos de `public/assets/`. O tema do admin (visual cyberpunk: fundo escuro com grid, neon ciano/magenta, fontes Orbitron/Rajdhani/Share Tech Mono) fica inteiro em `public/styles/styles-admin.css`, com tokens em variáveis `--cy-*`; ele só sobrescreve classes (Bootstrap, `.my-table`, `.model-table`, `.btn-add-product`, `.btn-modal`, `.form-default`...) e nunca depende de `c-id`. Fontes em `src/template/head.twig`, menu em `src/template/menu-admin.twig`, cores do gráfico em `home-admin.js`, TinyMCE com `skin: 'oxide-dark'` em `products-admin.js`; a página de login (`components/admin/login.twig`) usa o mesmo CSS. O JS usa o atributo `c-id` como seletor de elementos (ex.: `c-id="open-cart"`). Helpers compartilhados em `public/scripts/helpers.js` e `statusHandler.js`.
